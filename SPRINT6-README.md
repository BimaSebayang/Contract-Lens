# Sprint 6 — Compatibility Engine 🚧

> **Goal**
>
> Build the ContractLens Compatibility Engine to protect API consumers from contract changes through explicit compatibility decisions while maintaining a high-performance, non-blocking Spring Boot Gateway runtime.

---

# Sprint Objective

Sprint 6 focuses on evolving ContractLens from an API Contract Detection platform into an API Compatibility Platform.

This sprint introduces:

* Spring Boot Gateway
* Compatibility Engine
* Compatibility Plan
* Compatibility Rule Evaluation
* Runtime Transformation
* Caffeine Local Cache
* Backward Compatibility Protection
* Reactive Runtime Processing
* Cache-Miss Recovery
* Performance Optimization

The Compatibility Engine does **not automatically activate compatibility behavior whenever a contract change is detected**.

Contract changes are first detected and reported to the user. Compatibility protection is activated only when the user explicitly chooses to preserve backward compatibility.

---

# Technology Decisions

## Spring Boot

ContractLens continues to use **Spring Boot** as the primary application framework.

Spring Boot is responsible for:

* API Gateway runtime
* Compatibility Engine
* Runtime Transformation Pipeline
* Caffeine Cache integration
* Reactive request processing
* RabbitMQ integration
* MongoDB integration
* Compatibility Plan API
* Application configuration and dependency management

The Compatibility Engine is implemented as part of the Spring Boot architecture and must integrate directly with the Gateway runtime.

---

## Reactive Runtime

The Gateway runtime must remain **non-blocking and reactive**.

Runtime request and response processing should use Spring's reactive capabilities where applicable.

The Compatibility Engine must not introduce blocking operations into the Gateway request path.

### Runtime Principles

* No blocking database access
* No runtime contract comparison
* No synchronous remote dependency during normal compatibility lookup
* Compatibility lookup must primarily be performed from local memory
* Transformation execution must remain in-memory
* Runtime processing must remain reactive
* Compatibility Plan API fallback must use non-blocking communication
* Cache misses must not become the normal runtime path

---

# Compatibility Lifecycle

ContractLens separates compatibility into three major stages:

```text
Contract Detection
        │
        ▼
Compatibility Decision
        │
        ▼
Compatibility Execution
```

### 1. Contract Detection

Analyzer detects contract changes.

```text
Contract Snapshot
        │
        ▼
Contract Comparator
        │
        ▼
Contract Difference
```

The detected change is stored in `AnalyzeSpecDocument`.

---

### 2. Compatibility Decision

A detected contract change does not automatically activate compatibility.

```text
Contract Difference
        │
        ▼
User Notification
        │
        ▼
User Decision
        │
        ├── Reject / Ignore
        │
        └── Preserve Compatibility
                    │
                    ▼
          Compatibility Analysis
                    │
                    ▼
          CompatibilityPlan
```

The user explicitly determines whether the change should remain backward compatible.

---

### 3. Compatibility Execution

Once compatibility is activated:

```text
CompatibilityPlan
        │
        ▼
RabbitMQ
        │
        ▼
Gateway
        │
        ▼
Caffeine Cache
        │
        ▼
Compatibility Engine
        │
        ▼
Runtime Transformation
```

---

# Compatibility Plan

`CompatibilityPlan` is a **derived execution model** generated from contract differences and compatibility rules.

It is not the primary source of contract intelligence.

The source data remains:

```text
AnalyzeSpecDocument
        │
        └── ContractCompareResult
                │
                └── ContractDifference[]
```

The Compatibility Plan is generated by applying compatibility rules to those differences.

```text
ContractDifference
        │
        ▼
Compatibility Rule Evaluation
        │
        ├── Compatible
        │      │
        │      ▼
        │  Transformation
        │
        └── Unsupported
               │
               ▼
        Compatibility Report
```

Example:

```text
TYPE_CHANGED

expected = STRING
actual   = INTEGER

        │
        ▼

Compatibility Rule

INTEGER → STRING

        │
        ▼

TYPE_CONVERSION

sourceType = INTEGER
targetType = STRING
```

The resulting `CompatibilityPlan` acts as a **runtime execution instruction** for the Gateway.

---

# Compatibility Cache

Compatibility Plans are stored in an in-memory **Caffeine Cache**.

Characteristics:

* O(1) Lookup
* Thread-safe
* Local JVM Cache
* Primary runtime source
* No Database Lookup during normal Runtime
* Fast in-memory execution
* Cache synchronization through RabbitMQ
* Cache recovery through Compatibility Plan API

MongoDB remains the **Contract Intelligence Source of Truth**.

Caffeine is **not** the source of truth.

---

# Cache Strategy

ContractLens uses a combination of **Push Synchronization** and **Cache-Aside Recovery**.

## Primary Synchronization — RabbitMQ

When compatibility is activated:

```text
Analyzer
   │
   ▼
CompatibilityPlan
   │
   ▼
RabbitMQ
   │
   ▼
Gateway
   │
   ▼
Caffeine
```

RabbitMQ is the primary mechanism for synchronizing Compatibility Plans across Gateway instances.

---

## Cache-Miss Recovery — Compatibility Plan API

If the Compatibility Plan does not exist in the local Caffeine cache:

```text
Gateway
   │
   ▼
Caffeine
   │
   │ MISS
   ▼
Compatibility Plan API
   │
   ▼
Analyzer
   │
   ▼
MongoDB / Contract Intelligence
   │
   ▼
CompatibilityPlan
   │
   ▼
Caffeine
   │
   ▼
Compatibility Engine
```

The Compatibility Plan API exists primarily as a **cache recovery mechanism**.

It must not become the normal runtime dependency for every request.

---

# Cache Runtime Rules

### Cache Hit

```text
Request
   │
   ▼
Caffeine
   │
   ▼
CompatibilityPlan
   │
   ▼
Compatibility Engine
   │
   ▼
Transformation
```

### Cache Miss

```text
Request
   │
   ▼
Caffeine
   │
   └── MISS
        │
        ▼
Compatibility Plan API
        │
        ▼
    CompatibilityPlan
        │
        ├── Put into Caffeine
        │
        ▼
Compatibility Engine
        │
        ▼
Transformation
```

After the plan is loaded, subsequent requests should use Caffeine directly.

Compatibility Plans are derived from contract differences and compatibility rules.

```text
                 Analyzer

                            │

                            │

                     Runtime Lookup
                            │
                            ▼

                            │
                            ▼
                  Runtime Transformation
```

The Compatibility Plan acts as the **runtime execution instruction** for the Compatibility Engine.

The Gateway must not perform contract comparison during runtime.

# Cache Synchronization Strategy

Each Gateway instance maintains its own local Caffeine cache.

```text
                         RabbitMQ
                            │
              ┌─────────────┼─────────────┐
              │             │             │
              ▼             ▼             ▼
         Gateway #1     Gateway #2     Gateway #3
              │             │             │
          Caffeine       Caffeine       Caffeine
              │             │             │
              ▼             ▼             ▼
        Compatibility  Compatibility  Compatibility
           Engine         Engine         Engine
```

When a CompatibilityPlan is activated or updated, RabbitMQ distributes the update to Gateway instances.

Each Gateway updates its local Caffeine cache independently.

# Source of Truth vs Runtime State

| Component               | Responsibility                                         |
| ----------------------- | ------------------------------------------------------ |
| `AnalyzeSpecDocument`   | Contract Intelligence and historical contract evidence |
| `ContractCompareResult` | Detected contract differences                          |
| Compatibility Rules     | Determine whether a change can be protected            |
| `CompatibilityPlan`     | Derived runtime execution instruction                  |
| MongoDB                 | Contract Intelligence Source of Truth                  |
| RabbitMQ                | Compatibility Plan synchronization                     |
| Caffeine                | Local runtime cache                                    |
| Compatibility Plan API  | Cache-miss recovery                                    |
| Compatibility Engine    | Runtime transformation execution                       |
| Spring Boot Gateway     | Non-blocking runtime execution                         |

Compatibility Plans do not need to become a separate source of truth if they can be deterministically derived from the stored contract differences and compatibility rules.
